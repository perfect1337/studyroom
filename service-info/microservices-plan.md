# Study Room — план перехода на микросервисы (база данных на сервис)

## 1. Состав сервисов

| Сервис | Своя БД | Владеет |
|---|---|---|
| **User Service** | `study_room_users` | Пользователи, роли, филиалы, профили ученика/репетитора, связь родитель-ребёнок |
| **Academic Service** | `study_room_academic` | Курсы, записи на курсы, занятия, посещаемость, домашние задания и решения |
| **Contracts Service** | `study_room_contracts` | Договоры (сумма, даты, статус оплаты, статус договора) |
| **CRM Service** | `study_room_crm` | Заявки с сайта и внутренние заявки на курс |
| **Notification Service** | `study_room_notifications` | Отправка email/SMS/мессенджер, настройки каналов пользователя |

Каждый сервис — отдельный Go-процесс со своей PostgreSQL базой. Прямых SQL-запросов между базами быть не должно — только через API или события.

## 2. Как сервисы общаются друг с другом

### 2.1. Синхронно (REST, через API Gateway)
Используется, когда фронту или другому сервису нужен **свежий ответ прямо сейчас** — например, при логине, при создании договора (Contracts Service должен на лету проверить, что студент существует, вызвав User Service).

### 2.2. Авторизация без похода в User Service на каждый запрос
User Service выпускает JWT при логине. В токене — `user_id`, `role`, `branch_id`. Остальные сервисы **проверяют подпись токена локально** (общий публичный ключ) и сразу знают, кто обращается и какие у него права — не нужно ходить в User Service, чтобы просто авторизовать запрос. В User Service идут только за операциями именно над пользователями (создать, обновить, сменить пароль).

### 2.3. Асинхронно (события через брокер — NATS/RabbitMQ)
Используется, чтобы сервисы **не были жёстко завязаны друг на друга по времени отклика** и продолжали работать, даже если сосед временно недоступен. Механика: сервис-источник публикует событие в брокер, заинтересованные сервисы на него подписаны.

Ключевые события:
- `user.created`, `user.updated` — публикует User Service. Academic/Contracts/CRM подписаны, чтобы обновить свой локальный `user_refs` — облегчённую копию (id, имя, роль, branch_id) для отображения без постоянных REST-вызовов.
- `contract.expiring_soon`, `contract.status_changed` — публикует Contracts Service → слушает Notification Service (уведомить родителя/владельца).
- `lesson.created`, `attendance.marked_absent` — публикует Academic Service → слушает Notification Service (напоминание о занятии, уведомление родителю об отсутствии).
- `application.received` — публикует CRM Service (в том числе из webhook с Tilda) → слушает Notification Service (уведомить владельца/владельца филиала о новой заявке).

### 2.4. Локальный кэш вместо постоянных REST-вызовов
Academic/Contracts/CRM не хранят полные данные пользователя — только `user_refs` (id, ФИО, роль, филиал), обновляемую по событиям `user.*`. Это и есть тот самый компромисс database-per-service: имя студента показывается мгновенно из локальной копии, а не ждёт ответа от другого сервиса при каждой отрисовке таблицы.

### 2.5. API Gateway / BFF
Единая точка входа для React-фронта. Нужен, потому что некоторые экраны требуют данных сразу из нескольких сервисов (например, «Обзор родителя» — курсы и занятия из Academic Service + договоры из Contracts Service). Gateway параллельно дергает нужные сервисы и склеивает ответ, чтобы фронту не пришлось делать 3 отдельных запроса и синхронизировать состояние самому.

## 2.6. Матрица прав (owner / branch_owner)

Это не часть схемы БД — правила проверяются в API каждого сервиса на основе `role` и `branch_id` из JWT.

| Действие | Owner | Branch Owner |
|---|---|---|
| Смотреть расписание любого филиала | ✅ везде | ❌ только свой филиал |
| Редактировать/создавать занятия (`LESSONS.created_by`) | ✅ везде | ✅ только в своём филиале |
| Создавать/редактировать/удалять курсы | ✅ | ❌ |
| Записывать ученика на курс | ✅ | ❌ |
| Назначать репетитора на запись | ✅ везде | ✅ только своего филиала |
| Создавать учителей | ✅ | ❌ |
| Менять статус учителя (отпуск/больничный) | ✅ везде | ✅ только своих (в своём филиале) |
| Ставить учителю статус "неактивен" | ✅ | ❌ |
| Создавать учеников | ✅ | ❌ (только owner и parent) |
| Создавать/менять/удалять контракты | ✅ | ❌ |
| **Просматривать контракты (полностью)** | ✅ везде | ❌ **нет доступа** |
| Просматривать только дату окончания контракта | ✅ везде | ✅ только своего филиала |
| Финансовая отчётность (выручка, аналитика) | ✅ | ❌ |
| Просматривать заявки с сайта | ✅ | ❌ |
| Ученики/родители филиала | ✅ везде | ✅ только свой филиал |

Практическое следствие для Contracts Service: `GET /contracts` и `GET /contracts/{id}` (полные данные) отдаются **только owner**. Для branch_owner и parent есть отдельный урезанный эндпоинт `GET /contracts/{id}/expiry`, который возвращает только `end_date` — сумму, статус оплаты и остальные поля они вообще не видят ни в каком виде. Это не вопрос фильтрации одного и того же ответа, а два физически разных эндпоинта с разными DTO.

## 3. Подзадачи по внедрению (в порядке выполнения)

1. **Спроектировать API-контракты.** Для каждого сервиса — OpenAPI-спецификация (REST) до написания кода. Это фиксирует границы ответственности и позволяет фронту и другим сервисам начать работу по контракту, не дожидаясь реализации.
2. **Поднять User Service первым.** Все остальные сервисы зависят от него для авторизации — без него не с чем интегрироваться.
3. **Реализовать выпуск/валидацию JWT.** Общий механизм проверки подписи (например через общий публичный ключ или JWKS-эндпоинт), чтобы каждый сервис проверял токен самостоятельно.
4. **Поднять брокер событий** (NATS — проще для старта на Go, либо RabbitMQ) в Docker Compose, до того как писать логику публикации/подписки.
5. **Зафиксировать схему событий** — на каждое событие: имя, версия, JSON-структура payload. Без этого сервисы быстро разъедутся по формату данных.
6. **Реализовать Academic Service**: своя БД + REST API + подписка на `user.*` для наполнения `user_refs`.
7. **Реализовать Contracts Service**: своя БД + REST API + подписка на `user.*`, публикация `contract.*` событий.
8. **Реализовать CRM Service**: своя БД + приём webhook с Tilda + внутренние заявки + публикация `application.received`.
9. **Реализовать Notification Service**: подписка на события всех остальных сервисов + интеграции с email/SMS/Telegram-провайдерами.
10. **Поднять API Gateway/BFF**: маршрutization + агрегация ответов под конкретные экраны фронта.
11. **Docker Compose для локальной разработки**: каждый сервис + своя БД в отдельном контейнере, плюс контейнер брокера.
12. **Миграции по каждой БД отдельно** — свой набор migration-файлов на сервис (goose/golang-migrate), никакой общей схемы.
13. **Логирование и трейсинг** (например OpenTelemetry + Jaeger) — без этого отладка бага, размазанного по 3 сервисам, займёт кратно больше времени, чем в монолите.

## 4. Честная оговорка

Всё вышеописанное реально сделать, и модель для этого готова. Но стоит понимать цену: 5 сервисов, 5 баз, брокер событий, JWT-инфраструктура и Gateway — это в разы больше движущихся частей, чем монолит с одной Postgres, который мы считали раньше (~760–1000+ часов для джунов). На микросервисах эта цифра реалистично удваивается-утраивается, в первую очередь не из-за кода самих сущностей, а из-за инфраструктуры вокруг (брокер, Gateway, трейсинг, деплой пяти сервисов вместо одного).

**Альтернатива, которая даёт почти те же архитектурные плюсы дешевле:** модульный монолит — один Go-процесс, одна Postgres-база, но код и таблицы разложены по тем же 5 логическим модулям (пакетам) с чёткими границами и без прямых обращений к чужим таблицам напрямую (только через интерфейсы модуля). Если через год окажется, что какой-то модуль реально нужно масштабировать отдельно — его можно вынести в отдельный сервис позже, когда уже есть чёткие границы и трафик, который это оправдывает. Для команды джунов и текущего масштаба (один продукт, один рынок) это почти всегда правильный первый шаг — микросервисы имеет смысл вводить, когда монолит реально упирается в масштаб или в независимый деплой команд, а не заранее.

Если хотите, могу точно так же нарисовать ERD для модульного монолита — по сути та же схема, что я присылал раньше, просто с явным разделением на Go-пакеты вместо баз данных.
